## 1. 利用者との約束

通常運用は無操作とする。setupで設定した範囲内では、収集、整理、保存、再試行、復旧に都度の承認を求めない。正常時の完了通知も出さない。利用者が状態画面を見に行くことを前提にしない。

自動回復できる障害は自動で回復する。本人の操作が必要な障害、長時間の停滞、データ喪失の危険は、原因、影響、必要な操作を利用者へ通知する。通知は承認ダイアログにせず、通常作業を停止しない。

外部知能は論理的に1つ、整理AIは1つ、作業・記憶取得CLIは複数のまま維持する。個人ナレッジと任意のチームナレッジは既存の境界を保つ。整理AI停止中も既存知識の取得は継続する。

「完全自動」は対応環境における通常の処理経路を指す。AIが価値ある学びをすべて見抜くこと、失われた未取得データの復元、本人の再ログイン、電源OFF中の通知、通知の強制閲覧は保証しない。未確認のCLIを自動蓄積対応として表示しない。

## 2. 今回変えない境界

- 公開エンジンに個人ナレッジ、端末固有パス、認証情報を置かない。
- 生のプロンプト、応答、会話履歴、ツール出力、秘密情報、顧客機密を新たに保存しない。
- 生の会話履歴を後から読み直す収集経路は追加しない。取得元は許可された構造化記憶・要約・直接渡された再利用候補に限定する。
- 外部送信はsetupで設定された整理AIとデータ範囲に限定する。ローカルAIの選択をクラウドAIへの送信許可と解釈しない。
- 別の整理AIへの自動切替、追加課金、利用枠リセット、自動モデルダウンロードはしない。
- OS・CLIの承認、ログイン、通知拒否、集中モード、利用者による定期処理停止を迂回しない。
- 新しい常駐アプリ、通知用サービスへの登録、メール・チャット連携を必須にしない。
- setupの再実行・updateで既存の知識、identity、明示的な無効設定を初期化しない。

## 3. 現行実装と変更点

本節は仕様作成時のコード確認結果であり、実CLIでの動作証明ではない。

| 現行の要素 | 確認した内容 | この設計で追加・変更する責務 |
|---|---|---|
| `hook_entry.py` | 終了イベントを受信し、本文なしのキュー登録を行う | 受信と候補取得を分け、収集対象を永続登録する |
| `capture.py` / `adapters/` | 構造化候補の記録、記憶・要約の読み取り、重複照合 | 対象IDと収集結果を結び付け、取得可能な未処理だけを回収する |
| `queue.py` / `spool.py` | 永続キュー、ロック、再試行、暗号化一時保持、期限管理 | 整理待ち候補の保持期限・容量と回収状態を一貫して管理する |
| `maintainer.py` | 整理AIの呼び出し、状態遷移、保存、health出力 | 収集照合、障害分類、復旧照合、異常通知を連結する |
| `setup_activation.py` | Hook受信と定期処理の状態を分離。実運用は未確認扱い | 自動蓄積テストと通知テストの証拠を別々に記録する |
| `task_scheduler.py` / OS登録スクリプト | 任意の定期実行を管理する | 登録成功とは別に、実行実績と停止を検出する |

Skillの指示補強だけでは実行漏れを検出できないため、主対策にはしない。独立した常駐監視サービスも初版では追加せず、既存の定期処理とCLI起動経路を利用する。

## 4. 処理経路

```text
作業CLI / 対応アプリ
  ├─ Hookなどの通知 → 収集対象の登録
  ├─ Skill / 連携機能 → 構造化候補の受付・保持
  └─ 列挙可能な記憶・要約 → 差分走査による未処理回収
                         ↓
                  対象と受付記録の照合
                         ↓
                 選択済みの整理AI 1つ
                         ↓
            検証 → 追記型イベント → 索引更新
                         ↓
                 保存完了記録 / 次回取得

失敗・未処理 → 原因別の再試行または要対応 → 必要な異常だけ通知
```

Hookは短時間の登録・状態確認だけを行い、同期的に重い推論や全件走査をしない。整理AIの呼び出しは既存のmaintenanceへ集約する。点検、重複照合、通知判断ではAIを呼ばない。

### 4.1 対応能力をCLIごとに宣言する

各Host連携は、イベント通知、構造化候補受信、記憶・要約の差分列挙、処理結果の対象IDへの関連付け、利用者向け表示の可否を宣言する。単なる設定ファイル配置や実行ファイル検出を、対応能力の証明に使わない。

差分列挙できるHostでは、Hook未着でも取得元に現れた対象を回収する。列挙できないHostでは、受信済みイベント以外の網羅性を不明とする。候補を作業AIの任意のSkill呼び出しでしか取得できないHostは、記録忘れの独立回収を保証しない。

通知イベントのハッシュから失われた知識本文を推測して生成しない。利用可能な本文・要約がない対象を整理AIに渡して「保存不要」と判定させない。

Ollamaなどの推論Providerと、Hook・収集・利用者向け表示を担当するHostは別の能力として扱う。既存公開adapterと互換でないアプリは、新たな連携実装・契約テスト・実動作証拠が必要となる。

### 4.2 対象IDと受付完了

- 対象IDはHost ID、Host instance、取得元側のsession/turn/record識別子、対象範囲に基づき、信頼できる連携層が生成する。知識本文を含めない。
- 同一作業へのHook再送や複数ターンをまとめたcloseoutには、対象範囲を関連付ける。単一候補と単一ターンの一対一対応を仮定しない。
- 識別子が足りない場合は推測で別作業と同一視せず、追跡能力の制限を記録する。
- 元の作業対象の重複防止と、複数CLIから来た同内容の知識候補の重複防止を分離する。知識の適用範囲が異なる候補を誤って統合しない。
- 候補の形式・プライバシー検証、永続書き込み、対象との関連付けが完了してから受付完了を返す。ディスク不足・書き込み失敗時に成功応答しない。
- 走査cursorは候補または評価済み結果を永続化した後に進める。先にcursorだけ進めて対象を失わない。

### 4.3 収集と整理の状態を分離する

既存の整理キューを再利用し、その前段に収集状態を追加する。整理キューを二重実装しない。

| 段階 | 状態 | 次の動作 |
|---|---|---|
| 収集 | 収集待ち | 直接受付を待つ、または対応取得元を差分走査する |
| 収集 | 候補確保済み | 保持した候補を整理キューへ引き渡す |
| 収集 | 評価済み・候補なし | 対象範囲に結び付いた明示的評価の記録でのみ確定する |
| 収集 | 取得不能・追跡不明 | 原因と回収可能性を保持し、成功や保存不要にしない |
| 整理 | 待機・実行中・再試行待ち | 既存キューの状態遷移を使う |
| 整理 | 保存済み / 評価済み・保存不要 | 保存完了または有効な評価結果で確定する |
| 整理 | 要対応 / 隔離 | 通常作業を止めず、原因に応じて通知する |

「候補なし」と「保存不要」は知識の品質保証ではなく、処理が実行された証拠である。記録を受け取っていないだけの対象と区別する。NO評価の監査には固定理由分類・件数・識別子だけを残し、本文や自由文理由を長期保存しない。

### 4.4 回収元と読み取り制限

setupで設定されたHost所有の構造化記憶・要約のみを対象とする。任意ディレクトリへの探索拡大、Hook入力に書かれた任意パスの直接読み取り、会話ログへの代替探索をしない。

既存の安全なパス検証に従い、許可root外へのリンク、取得元の差し替え、未対応schema、過大なファイルを拒否する。差分走査は実行時間・ファイル数・入力量の上限を持ち、中断後に再開できる。削除・ローテーション・編集を、保存完了とは別の状態として扱う。

取得元の文章はデータとして扱い、記載された命令を実行しない。取得元から通知先、Provider、保存パス、許可範囲を変更させない。再試行中に同じパスの内容が変わった場合も、以前の候補の評価結果を別内容へ適用しない。

## 5. 整理が止まっても候補を保持する

新しい収集経路では、許容された構造化候補をまず端末内の暗号化pending領域に保持する。既存spoolとキューを拡張し、別のナレッジ・候補本文データベースや生履歴保管庫は追加しない。取得元のファイルパスや回収cursorは端末内runtimeだけに置く。

既存のSkillセッション別受付上限は未整理候補でも維持する。受付由来を明示した既存intentと旧journalを重複なく照合し、再送・同時受付・整理後にも上限を回避しない。未確定の受付枠予約は保持済み件数と分離し、同候補で再試行する。native取得へこの上限を拡張しない。

有界な巡回・移行・容量予約を支えるため、本文を持たないruntime-localなSQLite索引は利用できる。Python標準機能だけを使い、別アプリの導入を求めず、実DB/WALを公開リポジトリやknowledge同期へ入れない。索引の予約・計上値は、本文の現在の保有や収集coverageを実証する証拠ではない。本文使用時の認証を省かず、既存journalのsource of truthを置き換えない。

既にmanaged entryがある状態で索引が欠落・破損した場合、初版は安全側の要対応UNKNOWNとして新規の容量受付を停止し、元の本文・ID・TTL・journalを保持する。既知IDの安全な読取りは維持するが、全managed treeの自動再構築や容量の自動初期化は行わない。通常の中断はprepared/registered記録で復旧し、索引自体の破損と区別する。任意の外部改変の即時検出や、本文を失った後の再生成は保証しない。

鍵Providerが対象鍵を取得できないことだけでは本文の破損を断定しない。復号・本文開示・保持確認は失敗のままとし、元本文・容量予約・期限を維持するが、その失敗だけで恒久的な破損停止を作らない。後続で正しい鍵が使える場合は再認証と通常の容量検証を経て再開できる。実際の認証不一致・不正envelope等の検出済み破損、および呼出し側の参照不一致は区別する。

中断復旧では、書込みで構成が変わった保存shardも照合する。元の時間・件数予算内で照合しきれない場合は未確認を維持し、既存の許可済み予算内で再検証する。特に巨大なshardでは要対応となる場合があり、未完了の確認を成功扱いしたり、同じ先頭を無言で無限に走査したりしない。

本文ファイル作成前に中断した受付予約は、同じ候補・分類・用途・取得ID・元の作成時刻と期限への結び付きを検証して再開する。再暗号化で暗号文が変わっても、既存予約を超える容量を黙って追加せず、期限も延長しない。削除の記録後、実ファイル削除と容量計上の確定の間で中断し、対象が既に欠落している場合は、初版では削除完了を実証できない。容量予約を保持して要対応UNKNOWNとし、単なる欠落から容量を返却しない。この場合も既存knowledgeの取得や他の安全な既知IDの読取りは維持する。

既存のキュー・受付状態の更新がファイル置換前に中断し、登録済みの旧本文がそのまま残る場合は、旧digest・実サイズ・関連metadata・周辺の索引整合を検証したうえで未適用の更新予約を取り消し、旧状態から再試行できるようにする。未使用と実証した増分予約だけを精算し、既存本文・ID・期限は変更しない。新しい本文が既に保存されていれば通常の確定処理を行い、旧状態へ戻さない。欠落や不一致だけで取り消したり、削除後中断の予約を返却したりはしない。

受付済み候補が一時spoolの通常掃除で黙って消えないよう、pending状態と保持期限を連動させる。初版の保持設定は30日、上限1,000件または暗号化後64 MiBの小さい方とする。これらは新しいpending領域の初期値であり、既存利用者の保持設定を無条件で上書きしない。

期限切れの後始末がengine所有の一時ファイルの一過性エラーで止まった場合、所有writerの終了と安全性を確認できれば元の残予算内で再試行する。周辺の未知entryや他shardの異常を隠さず、終了不明のwriterのファイルは削除しない。期限切れの事実は本文削除より先に保存し、cleanupの失敗・解消は該当captureの証拠に限定する。

- 上限80%または最も近い保持期限まで24時間以下で、喪失リスクの通知対象とする。
- 容量上限では新しい受付を成功にせず、取得元側のcursorを進めない。既存候補の黙った追い出しは禁止する。
- 明示的な保持期限を超える前に通知する。期限到達時は本文を削除し、内容を含まない期限切れ記録と件数を残す。無期限保持や、期限切れを保存済み扱いすることは禁止する。
- 保存済み、保存不要、プライバシー拒否となった新規pending本文は既定の掃除で削除する。知識イベントに記録するのは既存の検証・昇格条件に従う内容だけとする。
- 既存の追記型知識イベントはこの移行で書き換え・削除しない。

保存直後・完了記録直前のクラッシュでは、対象IDと検証済みChangeSet・イベントの対応を照合して完了記録を回復する。知識の検索索引（projection）だけが未更新なら、推論をやり直さず知識イベントから再生成する。受付、推論開始、保存、完了記録の境目それぞれで再実行しても重複を増やさない。

時間予算付きのjournal読取り・重複検証・ChangeSet適用では内部にも元のdeadlineを渡す。初版の有界処理範囲は50,000 events、raw合計64MiB、単一raw8MiB、filesystem entries60,000、深さ8とする。途中の履歴を完全な集合として適用せず、時間切れ・固定上限・破損を区別して要対応を示す。固定容量上限は通常再試行や時間予算の増加で解決すると説明しない。元のjournalは書換えず、旧budgetなしAPIを維持するが、その手動実行が将来の自動処理上限も解消するとは扱わない。

manifest等からnamespaceを確証できない旧sourceも、同じ有界な巡回を使用する。架空のidentityで対応付けず、本文保存前のprivacy検査と保存済みroute/bindingを保ち、永続保存を確認してから進めるがcoverageはUNKNOWNとする。明示された単一fileの読取りを、その親や兄弟fileの探索許可へ広げない。自動directory探索の許可規則、no-follow、cursorの対象検証を維持する。

索引の有界更新では、既存knowledge内で完成・検証した不変の派生generationへ、root/index.jsonの単一atomic replaceで切り替える。これは別のknowledge正本ではなく、追記型journalから再生成できるprojectionである。未完成の子ファイルで旧索引を壊さず、読み手は検証済みgenerationへ結び付ける。人が開くroot/index.mdは完成generationへのリンクを持ち、期限切れによる更新遅れは明示し、次回maintenanceで新世代を始める前に直す。診断も同じ解決先を読む。不正なpointerや混合した版を正常として扱わない。

派生generationは現在・直前・準備中の最大3つ、各64MiB/120,000 files、合計192MiB以内に制限する。整理は元deadlineと所有確認の下で公開参照されない対象だけに限定し、未知のファイルやlinkは削除しない。片付けを確認できなければ新世代を追加しない。古い取得handleは2回以上の新しい公開後に明示的に失効し得るが、新しい取得は現在の完成版を解決する。準備中の再利用は名前だけで判断せず実データを検証する。これらの上限・一時的な閲覧入口の遅れ・失効は、無制限の自動復旧や常時最新として宣伝しない。

検証済みの推論結果も対象と内容hashに関連付け、保持期限内では再利用する。ただし、外部Providerが応答した直後・結果の永続化前にプロセスが落ちた場合、Provider側に重複防止機能がなければ再推論が発生し得る。試行と予算消費は実行前に記録して結果不明として扱い、保存の重複防止と、推論料金を厳密に一度にする保証を混同しない。

## 6. 自動復旧と実行量制御

| 原因 | 自動処理 | 利用者への通知 |
|---|---|---|
| 利用上限・レート制限 | Providerの再試行時刻を尊重し、候補を保持する | 24時間処理が進まず未処理が残る場合。保持リスクが先に来ればその時点 |
| 通信・ローカルAI停止・時間切れ | 同じ整理AIで間隔を空けて再試行する | 再試行上限後、または長時間停滞時 |
| 認証切れ・実行権限不足 | 自動更新が既存の公式認証機構で可能なら利用。それ以外は処理を保留する | 最初の確定時に必要な再ログイン・設定修正を通知 |
| 不正な出力形式 | 回数・実行量上限の範囲内で再試行する | 上限後に要対応。成功したことにしない |
| 取得元消失 | 確保済み候補で継続。未確保なら取得不能にする | 未確保対象が残る場合 |
| 定期処理停止 | 既存の有効な実行経路から未処理を再開できるようにする | 明示的無効化と故障を区別して通知 |

再試行は既存の300、900、3,600、21,600秒の待機を基本とし、以後も短い間隔に戻さない。Providerの指定が長い場合はそれを優先する。日次・実行単位の推論予算、時間、入出力量の上限を維持し、再起動で予算や試行履歴をリセットしない。

同じmaintenanceの残時間を、検証済み推論結果の暗号化保存/再読取りと判定後のqueue更新まで伝える。curatorの索引読取り・候補走査・返却前も同じdeadlineに含め、途中の集合から保存不要や新候補の確定を返さない。従来の昇格policy用budget引数とは区別し、照合・昇格・privacyの規則は変えない。初回の設定fingerprint登録は既存の保留状態を解除しない。設定変更は再試行の兆候であり、認証回復や問題解消の実証とは区別する。

同一Hostの同一障害はまとめて扱う。候補ごとの認証確認や、空キューへの定期的なAI呼び出しをしない。認証切れの間は公式の認証状態・設定変更などの低コストな復旧兆候を確認し、有償推論の連打はしない。復旧後は件数上限付きで滞留分を処理し、通常作業の資源を使い切らない。

認証復旧を自動判別できるtrustedな兆候がないCLIについては、再ログイン後に1回だけ明示的な「再開」を要求する例外を許容する。内部JSON編集を必要にせず、通常の保存・整理・再試行に確認を増やさない。この操作や資格情報の存在は認証成功の証明ではなく、同じ整理AI・既存予算・元の保持期限の範囲で待機候補を1回再試行する許可に限る。成功するまで認証incidentを解消せず、失敗や中断後に同じ許可を使い回さない。定期的な有償probeへの置換はしない。

故障からの再開と、利用者が無効化した設定の再有効化を混同しない。`--no-scheduler`や利用者による停止を勝手に解除しない。後者では自動整理が無効であることを表示するだけとする。

## 7. 異常検出と通知

### 7.1 検出経路

既存の定期処理とCLIの起動・終了経路で、同じ軽量なhealth判定を行う。定期処理自身が停止した場合も、次回CLI利用時に検出できるようにする。新しい監視AIや常駐サービスは追加しない。

未処理件数、最古の未処理時刻、最終試行、最終進捗、次回実行予定、通知送信状態を別々に記録する。空キューで保存件数が増えないことは故障ではない。登録だけされて実行されていない状態や、同じ失敗を繰り返して進捗がない状態は、正常なheartbeatで隠さない。

件数には全体確認済み・確認できた範囲のみ・不明の区別を付ける。部分確認は「確認できた範囲の件数（総数不明）」とし、不明は0件へ置き換えない。容量予約は保持確認と別に表示・判定する。索引/保存領域の確定した障害はProvider障害と分離し、固定理由で要対応を通知する。軽量cacheはbindingと有効期限を持ち、旧情報・部分情報から全体正常や復旧を推定しない。既存incidentの欠落した件数証拠は不明として扱い、障害自体と通知履歴は残す。

定期処理停止の判定は、OSの実行予定・結果と、実行可能だった機会を基準にする。初期閾値は2実行機会の未達とし、スリープ・電源OFF中の経過時間だけでは故障と断定しない。実行機会を確認できないOSでは未確認状態を返す。どの実行経路も動かない間の即時通知は保証しない。

初版macOSでは、取得可能なlaunchdの状態・最終exitと稼働時計だけからjobの再登録世代や2つの逸失機会を確証できない。同じ設定とruns値でもunload/reload後に再設定される反例があるため、逸失数は不明とし、固定理由SCHEDULER_GENERATION_EVIDENCE_UNAVAILABLEを返す。native読取り自体の非対応とは区別する。登録・通常実行・連続稼働の観測は保存できるが、それだけで停止検知の準備が確認済みとは扱わない。setupはこの能力の証拠をscheduler_monitorとして通常実行証拠と分け、未確認なら総合の無操作運用準備もUNVERIFIEDのままにする。

初版Windowsも、予定時刻やNumberOfMissedRunsだけから「PCと実行条件が利用可能だったのに失敗した機会」を確証できない。[Microsoftの公開仕様](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-tsch/191bcde5-dba5-4f8b-8e1f-b82b1bae6cbc)は後者にOS停止等による逸失を含む。登録/action・状態・実行結果・次回予定・稼働時計は独立観測し、実行可能な逸失数は不明、SCHEDULER_OPPORTUNITY_EVIDENCE_UNAVAILABLEとする。通常の実行実績や別の確認済み認証障害は保持するが、scheduler_monitorと総合準備を確認済みにしない。将来の実attempt receipt対応や常駐監視を初版の機能として説明しない。

Linuxの今後生成するsystemd timerには、前回の起動から設定間隔Nと2Nの2つの実タイマーを置く。正常にNで起動すれば両方の基準が更新されるため通常頻度は維持し、最初の起動が失われた場合にもう一つの起動機会を持たせる。判定ではOSの実タイマー配列と許容遅延・実行条件を確認し、旧単一タイマーに存在しない予定を作らない。既存登録を監視処理から書き換えず、旧形式で十分な機会を実証できない場合は未確認を明示する。既存登録の更新は、利用者が行うsetup/updateの所有権検証を通じて扱う。

### 7.2 表示経路

第一経路は、利用可能なOS標準通知。第二経路は、利用者に直接表示できることを実証したCLI固有の表示機構とする。

- Windows、macOS、Linuxそれぞれに小さな通知adapterを設ける。OS機能・ログイン済みデスクトップセッション・必要な実行機構を検出し、欠けていれば利用不能とする。追加アプリを黙って導入しない。
- 通知adapterは固定の実行先と引数・定型文を使う。候補本文、元パス、Providerの生エラー、シェル断片を実行文字列や通知へ入れない。
- Hookの機械可読stdoutへ警告を混ぜない。stderrが利用者に見えるとも仮定しない。AIへのcontext注入やSkillへの指示だけを、利用者向け通知の証拠にしない。
- CLI直接表示が非対応ならOS通知のみ。デスクトップがない場合は検証済みのCLI直接表示を利用する。両方が使えない場合は通知未対応とし、無人運用準備完了とは表示しない。
- ログファイルとstatusは診断用の第三経路であり、能動的な通知の代替には数えない。
- OSの通知拒否や集中モードを変更・迂回しない。通知送信に成功しても、利用者が見たとは判定しない。

通知文は原因、停止している機能、未処理件数、必要な操作を短く示す。本文・顧客名・作業名・秘密情報は出さない。件数は保持を確認した候補だけを数え、未確保の対象を「保持済み」と表示しない。

```text
外部知能：自動整理が停止しています
整理AIの再ログインが必要です。
未整理の候補12件は保持されています。
対応：設定済みの整理AIに再ログインしてください。
```

### 7.3 再通知と復旧

端末内にincident ID、固定理由コード、対象Host/Provider、初回検出、最終通知、送信試行結果、解決状態を保持する。

- 人の操作が必要な確定障害と喪失リスクは初回検出時に通知する。一時障害は自動復旧を優先し、上記の停滞条件で通知する。
- OSの同一incidentは原則24時間以内に繰り返さない。新しい重大化・喪失発生は別の通知更新とする。
- CLI直接表示は未解決incidentについてセッション開始時に1回だけ。同一セッションの毎ターン表示はしない。
- 送信失敗を送信成功として抑制しない。送信試行自体も最大1時間に1回に制限し、再起動で再通知制限を消さない。
- 復旧の実績を確認したらactive警告を解除する。過去のOS通知を消せない場合、既に通知したincidentに限り復旧通知を1回出す。単なる通知の既読・閉じる操作では復旧扱いにしない。
- データ取得不能のincidentは、認証復旧など無関係な成功で解決にしない。継続中の障害と、既に確定した喪失記録を分ける。

## 8. setup・update・実動作テスト

### 8.1 初回にまとめること

setupは、既存のHost・整理AI・保存先選択に、収集対象の範囲、利用する通知経路、必要な初回承認、自動テストによるAI利用をまとめて説明する。新しい選択肢を多数増やさず、対応Hostの標準設定を提示する。

収集や再試行のたびに許可を求めない。OS・CLIが求める初回承認や再認証は利用者に明示し、不要な権限拡大で省略しない。通知の表示確認が必要なら初回の確認にまとめる。単なる「承認した」という回答はHook受信や蓄積の証拠にはしない。

### 8.2 独立して記録する証拠

| 項目 | 必要な証拠 |
|---|---|
| 設定完了 | manifest、binding、root分離の検証 |
| Hook受信 | 対象CLIからの実際の受信記録 |
| 自動蓄積 | 合成の非機密作業で、候補受付、整理、保存、次回取得までの対応記録 |
| 定期処理 | OS登録・有効状態と、テスト実行の完了記録 |
| 通知 | 送信adapterの結果と、利用者向け表示の確認を分離した記録 |

CLIごとに能力・version・設定識別子・テスト時刻を結び付ける。実CLIテストは本物のCLIからHook・収集経路を通す。手作りpayloadや模擬Providerの成功を実CLIの証拠に流用しない。

テストは隔離したknowledge/runtimeで合成データを使い、利用中設定や個人知識を汚さない。Hostが安全な隔離起動を提供しなければ、その制限を表示し、実環境の一時書き換えを無断で行わない。テスト完了後は実運用bindingとの一致を別途確認し、隔離環境だけの成功を現在の運用状態へ無条件で転用しない。

初版の実CLI自動テストdriverは、安全な隔離起動の契約が確定するまで保留する。この範囲は利用者承認済みの残課題として保持し、該当する蓄積・recallの実証を`UNVERIFIED`と表示する。設定・既存receiptの分類・通知設定の実装とは区別し、模擬試験の合格で埋め合わせない。既存receiptの分類時も、同意外のCLI起動やversion取得を発生させない。

通知APIの受付だけなら「送信確認済み・表示未確認」。利用者が初回に実際の表示を確認した場合でも、その後の閲覧を保証する証拠にはしない。通知経路が確認できなければ設定自体は保持するが、総合結果は「設定完了・無人運用準備未確認」とする。

`check-only`では通知、AI呼び出し、OS登録、私有知識への書き込みをしない。非対話setupでは事前に指定された許可を使い、無限に回答を待たない。証拠が不足した項目は未確認のまま返す。

### 8.3 既存利用者の更新

旧データにはない収集状態を成功として捏造しない。旧キュー・イベントを読み取れる状態を保ち、新しい対象から追跡する。旧受信記録に対応候補がない場合は追跡不明とし、全件再推論や全文再収集を開始しない。

通知設定・許可・テスト結果は端末ごとに保持する。知識同期で他のPCの通知権限や到達性を引き継がない。同じ設定のsetup再実行で承認やテストを毎回要求しない。Host version、通知経路、bindingなど関連項目が変わった場合だけ、その証拠を未確認に戻す。

## 9. モジュール分割と実装順序

この節は責務と依存順序を示す。詳細設計の承認を受け、正確な変更ファイルとテストは上記の実装計画へ分離した。実装の完了を意味しない。

1. **収集追跡**：`hook_entry.py`、`capture.py`、`adapters/`との境界に、対象・受付・評価済み記録の小さな追跡モジュールを設ける。schema追加と旧形式互換を先に実装する。
2. **候補保持・回収**：`queue.py`、`spool.py`、`maintainer.py`を拡張し、cursor、期限、容量、クラッシュ後の照合を接続する。
3. **healthとincident**：原因分類・停滞判定を副作用のない関数へ分離し、定期処理とCLI起動経路から共用する。
4. **通知adapter**：OS通知と対応CLI直接表示を分離。incidentの重複抑制・再通知・復旧と接続する。
5. **setupと検証**：`setup_activation.py`、setup表示、CLI statusへ独立した証拠を追加し、実環境テストを実施する。

巨大な`maintainer.py`へ全責務を追加せず、新規の収集追跡・incident・通知機構は独立してテストできる単位にする。既存のjournal、適用範囲判定、Provider選択、チーム共有を作り直さない。

## 10. 合格条件

### 自動化・回収

- 初回設定済みの通常作業で、保存・整理・再試行の承認質問が0回。
- 候補通知の重複、同一内容の再送、並行CLI、同一session内の複数ターンで、処理対象を取り違えず重複保存しない。
- Skillが呼ばれなくても、対応する構造化取得元がある場合は差分走査で回収できる。取得元がない場合は成功ではなく取得不能・追跡不明となる。
- 候補未着を「保存不要」にしない。列挙不能なHostに全体の回収率100%を出さない。

### 保持・復旧

- 候補永続化前、永続化後、推論後、イベント保存後、索引更新前、完了記録前の中断から復旧できる。
- 利用上限、認証切れ、ローカルAI停止、不正形式で候補を黙って失わず、原因に合う再試行・要対応状態になる。
- 取得元消失、保持期限、容量上限、暗号鍵利用不能をテストし、受付成功・保持済みの虚偽表示がない。
- 予算・再試行回数・通知制限はプロセス再起動を挟んでも維持される。

### 通知

- OS通知の実表示、CLI利用者への直接表示、通知拒否、集中モード、デスクトップなし、送信失敗を各対応環境で区別して確認する。
- Hookのstdout形式を壊さない。AIが警告文を発話するかどうかに通知を依存させない。
- 同一障害を連発せず、未解決の再通知、復旧、喪失記録の扱いを確認する。
- 定期処理自身を停止した場合、次回CLI起動経路から停止を検出する。明示的な無効設定は再有効化しない。

### 安全性・互換性

- 生の会話、資格情報、顧客機密、私有パスを公開ファイル、通知、診断ログ、同期対象へ出さない。
- 取得元を不正パス・リンク・変更途中のファイルへ置き換えても、許可範囲外を読まない。
- maintenanceの原本deadlineはCLI入口のsource処理・lock取得から内部処理・ログまで共有する。期限後は通常の副作用を開始しない。取得済み資源の解放だけは、当該lockのno-follow・固定サイズ・取得時identity/tokenの一致確認に限定して行い、他のcleanupや追加の猶予予算へ広げない。確認できないlockは保存する。
- lock取得用に排他的作成した未公開tempは、その保持fdとno-follow pathのregular-file identity一致を証明できる場合のみ、1回の解放対象とする。未完成lockを公開せず、完全な所有記録を排他的に公開する。置換・link・確認不能なtempは保存し、新規予算や一般cleanupは認めない。
- 全対応OSで既存テストと新しい障害注入テストを実行する。実AI・実CLIの証拠は模擬テストやCIと分ける。
- 個人知識、任意チーム知識、旧インストール、`--no-scheduler`を保持したまま更新・再実行できる。

- 過去の対象IDやsummary対象範囲を、会話本文・時刻の近さ・最新session・同内容検索から推定しない。旧receiptは再分類しない。

### 12.2 接続方式

採用案は、**既存closeoutの適用処理に、独立したtrusted context検証と適用後の関連付けを接続する方式**。構造化候補と制御metadataは別引数・別生成元にする。

別案として、summaryを既存pending queueへ取り込み、maintenanceで関連付ける方式もある。ただし、既に評価済みのgate/changesetをqueueへ受け渡す契約まで拡張しなければ再推論が発生する。今回は既存の適用結果を再利用する採用案に限定し、queueの責務や課金経路を変えない。

流れ:

```text
Host連携の対象metadata + 構造化された候補/評価
  → namespace・session・scope・明示対象を検証
  → 復旧用のmetadataを保存
  → 既存の知識適用または明示NOの評価記録
  → 永続化された結果証拠を照合
  → 対象ごとのreceiptと関連付け完了を保存
  → 関連付け完了ACK
```

これはエンジン内部の動作順序であり、利用者に追加操作を要求する手順ではない。

### 12.3 trusted contextとHostの対応能力

Host連携が渡すcontextには、連携が実際に把握しているHost、instance、personal store、session、closeout recordの識別子と、**明示された対象集合**を含める。対象は各turn/recordのidentityとwork scopeを持つ。生IDは既存の方式でhash化し、候補本文には埋め込まない。

contextは、登録済みHost adapterの制御経路で生成する。候補stdin、gate応答、Skill出力、任意環境変数、自由な `--target-ids` 引数から同等のcontextを作らない。連携コード自身の実行は既存と同じ信頼境界内とし、同一OSユーザーによる悪意あるコード実行まで防ぐ認証機構とは主張しない。

境界の確認は次の全条件を満たすこと:

1. `capture_namespace` とinstall manifestで、現在のHost登録・instance・personal storeを照合できる。
2. 各対象が、Host連携から先に登録されたtarget bindingと一致する。bindingはcapture ID、identity、work scope hashだけを保持し、候補やパスを含めない。既存Hookの登録では確認できるmetadataだけを記録し、不足したbindingを後から候補本文で補わない。
3. 全対象が同じHost/instance/store/session/work scopeに属する。異なるturnは明示集合に含まれる場合だけ許す。同一session内でも、明示されなかったturnを追加しない。
4. work scopeは連携metadataのcwd fingerprintとdomainから生成する。domainが連携側で確定できない場合も不明とし、候補のdomainで補完しない。知識のHost applicabilityと作業scopeを混同しない。
5. 連携がcloseout recordと対象集合の対応を保証している。session終了イベントが届いただけでは、この条件を満たさない。

context不在・情報不足・未対応Hostは `UNKNOWN` / `CLOSEOUT_CONTEXT_UNVERIFIED`。他の対象receiptは変更しない。namespace不一致、別scope混入、未知の対象、対象集合の改変は関連付け拒否とし、正常な記録を上書きしない。

旧WAITING receiptにbindingがなくても、登録adapterから新たに届いたnative eventが現在のnamespace、同じcapture identity、session/turn、cwd/domainの照合を満たす場合は、その新しい証拠でbindingを登録できる。履歴や候補本文から欠落情報を推測して補うこととは区別する。これだけでreceiptを保存済みに変更せず、UNKNOWN・UNAVAILABLE・期限切れは昇格させない。既存bindingがある場合は同一semantic bindingだけを再送として許可する。

登録adapterには「明示対象付きcloseout contextを供給できるか」を独立した能力として追加する。既存adapterの既定値は未対応とする。contextを提供するadapterから共通closeout入口まで、実コードの呼出し経路を実装する。テスト内でreceiptを手組みするだけ、呼び出されない補助APIだけでは完成としない。

この追加により、Codex/Gemini等の全CLIが自動的に対象metadataを提供するとは宣言しない。各Hostへの対応宣言には、そのHostが保証するmetadata契約と連携の実動作証拠が必要。未対応Hostの既存蓄積・closeout自体は壊さず、関連付け能力だけを不明と表示する。

### 12.4 適用結果と受付結果を分ける

候補の処理結果と関連付け結果は独立させる。例えば知識の適用が成功しても関連付け保存に失敗した場合は、`knowledge=APPLIED` / `association=PENDING` とする。再実行のために、適用済み知識を消したり全体を未実行扱いに戻したりしない。

新しいtrusted関連付け経路は、既存形式の構造化されたYES/NO評価を受け取る。評価がない候補のために新しい推論を開始しない。既存の通常CLIが持つ評価・推論動作は維持するが、それを関連付け機能の追加呼出しとして再実行しない。

- YES: privacy/gate/changesetの既存検証後、実際の `curation.changeset.applied` marker、そのchangeset hash、参照先イベントの完全性・Host/scopeを照合してから `SECURED` を記録する。NO_CHANGEや候補生成だけを知識保存証拠として扱わない。
- 明示NO: 検証済みの評価とtrustedな対象集合を結び付けた、本文を含まない評価完了記録を先に永続化する。その記録を確認して初めて `EVALUATED_NONE` にできる。候補未着・context不在・評価失敗をNOに変換しない。
- DEFERRED、FAILED、privacy拒否: 関連対象を保存済み・評価済みへ進めない。既存の候補保持・再試行・障害表示を維持する。
- `changeset_ready` は提案のままとする。配布Skillの現在の出力だけで `SECURED` や完了ACKを作らない。通常CLIと配布Skillにそれぞれ回帰テストを置く。
- content dedupと対象追跡を分離する。同じ内容でも別対象の受付事実は消さず、既存の知識重複判定とHost applicabilityを変更しない。

### 12.5 永続化、再送、中断復旧

追加のmetadataはruntime内だけに保存し、知識同期の対象にしない。識別子・hash・UTC timestamp・固定reason code・結果への参照だけを許可し、生本文、raw prompt/response、個人パス、資格情報を保存しない。schemaで未知のfieldを拒否する。

処理単位は、連携が発行したcloseout record IDとその対象集合。対象集合を正規化してhash化し、候補・評価・evidence・applicabilityの意味的fieldのfingerprintと固定する。受信日時・再試行回数をこのfingerprintに混ぜない。同一record IDの再送では同じ集合・同じ内容だけを受け付け、変更があれば `CLOSEOUT_CONTENT_CONFLICT` / `CLOSEOUT_TARGET_CONFLICT` で拒否する。内容の似た別recordを同一処理と推測しない。

検証済みのchangesetまたは明示NOの評価は、既存の暗号化 `validated-result` spoolに一度だけ保存する。新しい本文保存方式やqueueは作らない。spoolのpurpose・capture IDによるAAD binding、privacy検証、容量計上、期限、safe_fsを共用し、メタデータ側にはSpoolRefだけを置く。changesetのID・generated_at・fingerprintは初回の値を固定し、再開時に作り直さない。未適用の結果本文はこの暗号文から復元する。

永続化順序:

1. 検証済みcontext、対象bindingのdigest、期待するchangeset/評価記録のID・hashを持つ `PREPARING` intentを予約する。予定のspool IDは処理世代から決定し、書込後のSpoolRefと `PREPARED` をatomicに保存する。spool書込前後の中断も同じIDで照合し、別本文による上書きや二重容量予約をしない。
2. 保存した結果を検証してから、既存closeoutの適用処理を行う。変更イベント群の一部だけが存在し適用markerがない場合、適用済みと判断しない。
3. 完全な結果証拠を確認した後、capture lockの下で各対象receiptを冪等にmergeする。各receiptは実際に確認した自分の関連だけを表し、未完了の別対象も完了したような集合を先に公開しない。
4. 全対象の結果を再確認してから関連付け状態を `COMMITTED` にし、ACKを返す。一部のreceipt更新後に失敗しても全体完了ACKを返さない。
5. 再送・定期処理は保存済みの結果とmarkerを照合し、不足した適用またはmetadata更新だけを再開する。既存のUNKNOWN、期限切れ、content conflictを成功で塗り替えない。cache・intentの削除は全receiptの完了確認後とし、cleanup失敗を未保存の知識と混同しない。

`apply_changeset` の `ALREADY_APPLIED` は互換性のため従来どおりevent_idsを空で返す。その戻り値に、既存処理が実際に発見・保存したmarkerのID、元のoccurred_at、保存済みchangeset hashだけを持つoptional参照を追加する。既存のapplied/reason/event_ids等の意味は変更しない。参照は探索用の手掛かりであり、検証済み証拠や受付完了ではない。追加の永続索引・探索・推論は作らない。

共通のread-only結果証拠取得は、元の参照から既存規則で構成したevent partition/IDを直接読み、markerと全参照イベントを照合する。候補由来の任意パスを読まない。要求changesetは初回cache値を変えず、照合のためだけにgenerated_atを実markerのoccurred_atへ置換した一時値を作る。この一時値のfingerprintとmarker hashが一致する場合に限り時刻差を許す。operations、source hashes、candidate、policy、provider、Host applicabilityの差は許さない。元のhashを新しいhashへ置き換えず、知識結果には検証済みの元hashを返す。適用証拠と対象のHost/work scope照合は両方必要で、NO_CHANGEだけで知識確保にしない。

crash順序は、初回changesetの暗号化cacheを固定→applyから元marker参照を取得→参照を既存intentへatomic保存→read-only検証→receipt更新→全件再読込→COMMITTED、とする。参照保存前に中断した場合は、認証済みcacheから同じchangesetを既存applyへ再度渡して参照を回収できる（既存の重複照合を利用し、Providerは呼ばない）。参照保存後は直接lookupで復旧する。cacheも参照も失われた状態から全履歴検索や推論で補完しない。cacheを失っても元参照と十分な照合証拠が残っている場合だけ保存済み知識の復旧を続ける。

結果cache保存前に中断し、認証済みの結果本文も適用証拠もなければ、関連付けは未確定のままとする。Host側の未ACK候補の再送・既存の取得元回収を待ち、metadataから本文を再生成しない。連携が再送や永続取得元を提供しない場合は回収不能の限界を明示する。未適用cacheの期限切れ・喪失は先に喪失状態を保存してから既存規則でcleanupし、再送で元の期限を延長しない。完全な適用markerが既にある場合は、cacheの消失だけを理由に保存済み知識を失ったと扱わない。

### 12.6 有界処理と安全性

- 1 closeoutの対象は最大64件、metadata recordは最大16KiB。超過時は全件を拒否し、黙って先頭だけを関連付けない。
- 新規の未完了associationは最大64件・合計1MiB。予約は排他lock内で行い、不完全なinventoryを空と扱わない。容量が不足すれば新規受付を止め、既存intentを保持する。既存spoolの容量・TTLを増やさない。
- 完了済みintentは全対象receiptの永続化と再読込を確認後にcleanupできる。receiptとtarget bindingに再送照合用の世代・digestを残し、cleanup後も対象集合の改変やcontent conflictを検出する。既存receiptに証拠がない旧データは推測で補わない。
- 保守処理は既存maintenanceのdeadlineを共有し、1回最大64件をmetadata indexのcursorから回収する。予算切れでcursorを完了扱いに進めず、AIや別のschedulerを追加しない。
- 2026-10-05の利用者確認により、中断復旧だけに使う本文なしの未完了一覧（最大64件）の追加は許可済み。このruntime内の一覧を、禁止している新しい知識検索索引・changesetからmarkerを逆引きする索引と区別する。知識検索・journal探索の索引や新しい推論経路は追加しない。
- capture lockを保持したままProviderを呼ばない。既存のcapture→spool→queueのlock順を逆転させず、関連付け段階は知識適用のlock解放後に行う。
- すべてのread/write/cleanupに既存safe_fsのcontainment・no-follow検査を適用する。破損、link、置換、書込失敗では証拠を保全し、成功ACKを出さない。
- 新しい通知経路を作らない。関連付け未完了・容量不足の固定診断codeを既存health/incidentに接続し、既存の通知無効化・間隔制限を守る。

### 12.7 責務と実装範囲

新規のcloseout-associationモジュールに、context検証、prepared/committed metadata、receipt関連付け、復旧を集約する。既存モジュールの変更は、Host adapterの能力とcontext供給、target binding登録、CLIの共通closeout接続、結果証拠のread-only取得、maintenanceの有界復旧呼出し、関連するschemaに限定する。

巨大なCLI/maintainerへの直接実装、無関係な整理、既存DB/知識の一括移行、インストール済みSkill・認証・OS通知・定期処理の実環境変更は本追加の対象外。正確な所有ファイルとAPI signatureは、本設計の確認後にLuna向け実行書へ固定する。

### 12.8 合格条件

1. 登録adapter→trusted context→共通closeout→実journal適用→複数の実receiptまでを、一時rootとfake providerで通す。候補保存と対象関連付けを同じテスト内の証拠で追える。
2. 同じsessionの明示された2turnだけを関連付け、同sessionの未指定turn、別Host、instance、store、session、cwd/domainを変更しない。
3. 候補本文・gate出力に他対象IDや制御fieldを混ぜても、それをcontextや対象集合として使用しない。未知・不足・改変contextでは成功ACKを返さない。
4. 同じcloseout再送は知識・推論・receiptを二重計上しない。同じrecord IDで本文・対象集合を変えた再送は拒否する。同内容の別recordと別scopeも区別する。
5. prepared保存前後、知識イベントの途中、適用marker直後、receipt更新の途中、commit記録直前、ACK直前で中断させる。再開時に存在しない証拠を作らず、保存済み知識を失わず、余分なProvider callを行わない。
6. YES、明示NO、DEFERRED、FAILED、privacy拒否、提案のみのSkillについて、知識状態と関連付け状態を別々にassertする。
7. markerのhash不一致、参照イベント不足、metadata破損、期限切れ、容量上限、deadline、同時実行、link置換を試し、ACK・cursor・予約・既存receiptの保存を確認する。
8. setup/updateを再実行しても、既存knowledge、store identity、通知・schedulerの明示無効設定を保持する。既存CLI/Skill payloadは互換性を保ち、対象metadataがない呼出しの関連付けはUNKNOWNのままとする。
9. 新規対象テスト、既存全体unittest、固定差分レビューを通す。実CLIの対象metadataと自動連携を未確認のまま「全CLI対応」と表示しない。既存の公開export・履歴監査・新SHAのCI gateは省略しない。

### 12.9 チーム共有判定の再送・復旧（2026-10-06承認）

チーム共有の判定結果も既存の保存処理へ含める。新しい索引、queue、本文保存方式は追加しない。個人のみの利用、legacy CLI、保存拒否の挙動は維持する。

- trusted closeout初回prepareで、個人changesetとチーム判定（共有対象・明示的な対象外・無効・判定失敗）を既存の暗号化validated-resultへ一緒に保存する。公開済みの判定API・privacy規則・選択済みProviderを再利用する。チームへの書込みは、個人知識の実適用証拠を検証するまで行わない。
- 再送とmaintenance recoveryは保存済みの判定を使用し、新しい共有判定の推論を呼ばない。共有不要の結果がない旧記録や保存前の中断を、共有不要や成功として補完しない。失われたProvider応答を復元・再推論したと主張しない。
- チームへの引渡しでは、検証済みの実際のchangeset hashとevent IDsを引き継ぐ。候補hashへのfallbackは禁止する。イベント時刻・ID・冪等キーを再開時にも同じ値にし、直接保存・既存outboxへの引渡しの中断で二重化しない。
- 共有対象外/無効は本文なしの確定結果を既存associationへ残す。共有対象は保存済み判定から既存team event/outboxへ耐久引渡しし、再読確認した結果をassociationへ記録してから結果本文をcleanupする。未完了なら同じ復旧一覧・予約・TTLと暗号文を保持し、既存maintenanceから再開する。
- 共有の判定・引渡しが失敗しても個人の適用済み知識を取り消さない。結果が不明な共有は明示PENDING/UNKNOWNとし、個人適用とチーム完了を混同しない。容量・期限・破損・設定先変更でも追加推論や成功補完をしない。
- 本文は暗号化spoolのみ、associationはhash・固定status/reason・必要最小限の参照のみ。既存16KiB/64件/1MiB上限、safe_fs、同一deadline、lock順、通知disableを維持する。capture lockを保持してProviderや共有先I/Oを呼ばない。
- 合格条件はteam有効の初回→compact再送（Provider1回、同じ実hash、重複event/outboxなし）、明示対象外の再送（Provider1回）、個人適用後・共有保存前後の中断復旧（Providerなし）、outbox引渡しと欠落/破損/期限の非成功、team無効・legacy・既存privacy拒否の互換とする。
